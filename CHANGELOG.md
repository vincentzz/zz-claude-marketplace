## 0.9.6 (dev-pipeline, dev-pipeline-cn) · 0.1.2 (trade-study, trade-study-cn)
- **The environment could not override the agents' model.** Found running the pipeline on a second machine: `CLAUDE_CODE_SUBAGENT_MODEL` was set to a model that machine actually has, and every subagent still launched on the `fable`/`opus` named in its frontmatter. Claude Code 2.1.251 reversed the precedence — per-call parameter > frontmatter > `CLAUDE_CODE_SUBAGENT_MODEL` > main session — and since every agent here names a model, the variable alone now reaches nothing. Measured on 2.1.258 with a probe whose frontmatter says `model: sonnet`: `CLAUDE_CODE_SUBAGENT_MODEL=opus` alone → ran on claude-sonnet-5; with `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` → claude-opus-5; `ANTHROPIC_DEFAULT_SONNET_MODEL=claude-haiku-4-5-20251001` → claude-haiku-4-5.
- The `model:` lines stay, but they are now documented as **tier names the environment is expected to rebind**, with two harness-enforced ways to do it: rebind the tiers with `ANTHROPIC_DEFAULT_{FABLE,OPUS,SONNET,HAIKU}_MODEL` (keeps the matrix, every version, main session included), or pin every subagent with `CLAUDE_CODE_SUBAGENT_MODEL` + `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (≥ 2.1.257; the main session needs `--model` separately). New README section *Running where a different model set is available* plus a Known-pitfalls entry; the trade-study READMEs carry the short form.
- architect A0 now runs `printenv` on the two variables: a pin switches the model gradient off for the session (a per-call parameter would be overridden anyway, and the deviation notes would be lies); the variable without `_FORCE` gets a one-line warning that it is not taking effect. The agent file used to say the opposite — "never set CLAUDE_CODE_SUBAGENT_MODEL, it swallows the per-call parameter" — which was true before 2.1.251 and is the trap now.
- Retired two stale claims: the Agent tool's `model` enum includes `fable` on current versions (the failure-upshift step sonnet→opus→fable is now reachable), and the local-fallback launcher now also sets `ANTHROPIC_DEFAULT_FABLE_MODEL`, so the README's "tier-mapping env vars as a backstop" is finally true for the two `fable` roles. The launcher keeps rewriting frontmatter rather than using `_FORCE`: that is the only way to give the reviewers a different model from the rest, and it works on every version.

## 0.1.5 (websearch-tool)
- **The machine-global pacing was not machine-global.** State lived under `tempfile.gettempdir()`, which honours `$TMPDIR` — on macOS a per-user, sometimes per-session sandbox (`/var/folders/<hash>/T/`). Agents landing in different sandboxes each got their *own* `.pace-ddgr` lock and `.ddgr-strikes` counter, so the serialization built in 0.1.1–0.1.3 could silently degrade to per-agent, i.e. to nothing, in exactly the parallel-scout fan-out it exists for. State now lives in `/tmp/claude-web-<uid>` (0700, ownership-checked because `/tmp` is world-writable; `WEB_STATE_DIR` overrides). Verified: two processes with different `$TMPDIR` values now serialize on the same lock (5.1s wait), where before they would not have contended at all.
- SKILL.md now forbids calling `ddgr`, `curl`, or a browser directly, and says why: every safeguard — shared pacing, backoff, `Retry-After`, the `CHANNEL`/date/`SAVED` provenance line — lives in the script, and a bare `ddgr` call can soft-block the machine for every other agent. Prompted by a real scout run that loaded the skill and then appears to have improvised its own calls, leaving no result files behind.
- Also states that each call is synchronous — the same run showed the agent planning work to do "while the search runs", which nothing in the script supports.

## 0.1.4 (websearch-tool) · 0.1.1 (trade-study, trade-study-cn)
- **The skill was loaded and the scout still did not reach for it.** Found in a real trade-study run: scout tried `WebSearch`, it failed, scout tried `WebFetch`, and then stopped — never trying the `web-search` skill that was sitting in its skill list. Two causes, both fixed.
- The skill description led with *why* the built-in tools might be missing (`— the normal case when the session runs against a non-Anthropic endpoint`), which reads as inapplicable to a model on Anthropic whose `WebSearch` merely errored. It now leads with the **symptom** — errored, empty, timed out, denied, or absent — and states explicitly that the cause does not matter, plus "do not answer from training data before trying this".
- scout (both variants) gains a hard rule: **a failed search is not a finding**. A tool that errors or returns nothing means the criterion is *not researched*; the scout must try the `web-search` skill, and if that is unavailable too, declare the gap naming what could not be retrieved. Previously nothing in the agent prompt covered the failure branch at all, so the scout fell back on training data — the exact failure the provenance discipline exists to prevent. A skill description is a weak signal next to an agent's own process; the agent needed to name it.

## 0.1.3 (websearch-tool)
- **The backoff could outlive the tool call that invoked it.** A model follows SKILL.md and runs `web.py search "…"` with no explicit timeout; Claude Code's Bash default is 120s. From one strike on, the ladder exceeded that (80s × up to 3 queries = 240s), and a blocking `flock` behind another agent's 600s hold had no bound at all. The process was killed and the model got **zero output** — no `CHANNEL`, no `UPSTREAM:`, no backoff figure. The "fail loudly, never silently" contract inverted exactly where it mattered most.
- Every invocation now budgets ~100s of wall clock (`WEB_TIME_BUDGET`). When a gap, a lock queue, or a `Retry-After` would outlast it, the script stops and emits a new **`BACKOFF`** channel naming the seconds owed and what still works. `paced()` returns the debt instead of sleeping it; lock acquisition polls `LOCK_NB` against the same deadline. This is the rule the 429 branch already followed — `RETRY_WAIT_MAX` (120s) also exceeded the budget and is now bounded by it too.
- **Strikes now decay after 30 minutes** (`WEB_STRIKE_TTL`), keyed off the strike file's own mtime, with pure reads deliberately not refreshing it. Previously a counter only cleared on a *successful* search, so a run that accumulated strikes and stopped left the penalty in `$TMPDIR` — and tomorrow's unrelated first search paid up to 600s for a block that expired hours ago, then died silently per the bug above. The one real block measured here outlasted 7 minutes, so 30 leaves margin.
- Known and deliberately not built: backoff is per-backend, not per-host (a `429` host gets `Retry-After` honoured once, nothing persistent), and `retry_after` parses integer-seconds only — the HTTP-date form falls back to the default wait.

## 0.1.2 (websearch-tool)
- Finished the concurrency work 0.1.1 started. The pace lock was correct, but two *other* pieces of shared state were still racing, and both errors shortened the backoff rather than lengthening it — the wrong direction for a plugin whose job is to stay unblocked.
- **Strike counter was an unlocked read-modify-write.** 20 concurrent increments landed as 18. Worse, `write_text` truncates before writing, so a concurrent reader could catch the file empty and read 0 — silently resetting the backoff that 0.1.1 advertised as persistent (measured: 216 bad reads in 8000). Now flock + `pread`/`pwrite` on the locked fd: 20/20 across five runs, 0 bad reads in 8000.
- **The gap was computed before joining the lock queue.** A process that queued behind a 300s wait used the strike count from when it arrived, ignoring throttles recorded while it waited. `paced()` now takes a callable evaluated under the lock.
- Result files are written to a temp name and `os.replace`d, so a concurrent agent reading a `SAVED:` path never sees a half-written file.
- Documented lock order (pace → strikes, never the reverse) and the flock caveat: fine on a local `$TMPDIR`, not dependable over NFS/SMB.

## 0.1.1 (websearch-tool)
- Retuned for **unattended availability over throughput**: an agent that gets itself blocked at 03:00 has failed; one that took 20s longer has not. Search gap 2.5s → **20s**, plus a new **1.5s per-host gap on fetch** (there was none). Both override via `WEB_SEARCH_GAP` / `WEB_FETCH_GAP`.
- **Fixed a race that defeated the pacing entirely.** The old stamp file was read without a lock, so N agents starting together all saw a stale timestamp and fired simultaneously — precisely the burst that gets a session blocked, and precisely what trade-study's parallel scouts do. Pacing now holds an `flock` *across* the sleep, so concurrent processes queue one gap apart. Measured: 5 concurrent searches went out at +1.4/4.1/6.3/9.3/12.3s under a 3s gap.
- **Backoff that survives process exit.** Each suspected throttle escalates the search gap ×4 (20s → 80s → 320s, cap 600s), persisted in a strike file — a backoff that resets per invocation is not a backoff. A success clears it.
- **`429` is now honoured rather than immediately retried.** Reads `Retry-After` via curl's `%{header_json}` (older curl without it falls back to 60s), waits up to 120s, and beyond that reports the pause the server asked for instead of blocking or hammering. `403` still retries at once with a browser UA — that is a UA block, not a rate limit.
- **DuckDuckGo's soft block is now named.** ddgr exits 0 printing `[]` while saying `HTTP Error 202: Accepted` on stderr; that line was being discarded, which is the *only* thing distinguishing a throttle from an empty index. It is now surfaced as `UPSTREAM:` and promotes the status from `EMPTY-OR-THROTTLED` to `THROTTLED (upstream said so)`.
- The `/llms.txt` probe is cached per host. It was firing an extra request on every HTML fetch — doubling the request rate against the very host being read.
- Verified against a real throttle: testing tripped DuckDuckGo's 202 block, so both the detection and the escalation paths are now exercised for real rather than only by simulation.

## 0.1.0 (websearch-tool)
- New **websearch-tool** plugin (always-on, `defaultEnabled: true`, no `entryAgent` — a utility, so `/use-profile` never disables it when binding a profile): one skill, `web-search`, giving every profile web access that survives switching the provider away from Anthropic, where the built-in `WebSearch`/`WebFetch` tools simply cease to exist.
- Tiers, ordered by availability rather than by quality: **built-in first** (this skill neither duplicates nor disables them) → **curl fetch**, which needs zero setup and rewrites URLs to JS-free sources (github.com → raw/API, npm/PyPI/crates → registry JSON, plus an `/llms.txt` probe on doc sites) → **ddgr search**, best effort, needs `brew install ddgr` → **headless render**, on detection only, never on prediction.
- Every result carries `CHANNEL` (`builtin | ddgr-best-effort | curl | raw-api | rendered | RENDER_REQUIRED | NO-BACKEND`) + retrieval date + the query/URL, and lands in a file under `$TMPDIR/claude-web/` whose path is reported — downstream profiles require a source and a date on every factual claim, and the channel says whether the evidence is mechanically reproducible or scraping to be discounted.
- Failure is loud and actionable, never silent: `NO-BACKEND` prints both working paths (supply a URL — fetch needs no setup; or install ddgr), `RENDER_REQUIRED` names the page as unretrieved and forbids filling it in, and an empty ddgr result is reported as **EMPTY-OR-THROTTLED** rather than "no results found" — the two mean opposite things to a reader.
- Measured, not assumed: the fetcher identifies honestly as curl and only retries with a browser UA on 403/429. A spoofed Chrome UA is what *triggers* Cloudflare blocks (403 where plain curl gets 200), because bot managers fingerprint TLS and header order.
- Deliberately deferred: no MCP server (needs per-user config — this plugin exists because a plugin can ship a script but not an MCP config), no SearXNG, no API-key backends, no engine scraping beyond ddgr. bash + python3 only; node is touched only when tier 4 fires.

## 0.1.0 (trade-study, trade-study-cn)
- New **trade-study** profile plugin (and **trade-study-cn**, its Chinese twin): structured comparison of solutions/tech stacks for decision-making. Three roles — analyst (entry agent, main session: interview → brief → synthesis → deliverables), scout (one per candidate, parallel, structurally isolated from the other scouts' findings), challenger (one adversarial pass over the synthesis, [BLOCKING]/[SUGGEST], ≤2 rounds).
- Decisions recorded at birth: scoring is **ordinal + user weights** (`--`…`++` mapped −2…+2 — no fake numeric precision); scout research **depth is set per study in the brief**; deliverables (single-source `synthesis.md` → HTML + PDF + PPTX decision brief) use a **designed** aesthetic, not a default theme; **bilingual from day one** (EN + CN variants), deliverables follow the brief's language in both.
- Deliberately thin mechanical layer: no task queues, worktrees, or gates — analysis has no ground truth to turn from red to green, so structural adversity (provenance discipline, scout isolation, challenger arithmetic/completeness checks) substitutes for mechanical acceptance. 3 agents, 5 skills; every future addition needs evidence from a real study.
- Both manifests declare `entryAgent: analyst` + `defaultEnabled: false` — /use-profile discovers and binds them like any profile. Enable at most one of the pair per project (same agent names).
