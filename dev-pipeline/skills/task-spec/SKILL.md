# 写 task spec

spec 是 architect 与 qa、dev 之间唯一的合同文本。qa 只测 spec 写了的，dev 只做 spec 写了的——所以 spec 里没写的等于不存在，写含糊的等于埋雷。

模板：`tasks/specs/_template.html`（`taskctl add` 会自动实例化）；满分示范：`tasks/specs/_example.html`。

## 各节完成判据

1. **背景与目标** —— 全部来自 grill-me 的已决结论；出现"待定/大概/可能"即未完成。
2. **Deep Module 设计** —— 按 `/deep-module-design`（边界三分法：必须知道 2.1 / 不需要知道 2.2 / 不得知道 2.5）：
   - 2.1 接口：**可编译级完整**的签名 + 契约注释。qa 将一字不差地落成骨架，所以少一个 `throws`、错一个泛型都会变成流水线事故。性能敏感的接口在此标注热路径（切换 dev 的风格优先级），重要的性能约束配机械 AC。
   - 2.2 只写"藏了什么"，不写"怎么做"——qa 也读本节。实现提示写 `specs/<id>/architect/dev-hints.md` 并列入 2.5 的 qa 禁知。
   - 2.3 失败归属表：每行四列填满，判定依据机械可断言。
   - 2.5 禁知：只列基线（CLAUDE.md）之外的增量，每行有理由与替代来源；无增量写"仅基线"。自查：qa 写测试所需的一切都已在 2.1/2.3/3 里了吗？不够就补 spec，而不是留缺口逼 qa 去翻不该翻的东西。
3. **验收条件** —— 每条 AC 一行五列：编号、行为描述、判定命令、通过标准（恒为 exit 0）、承载测试（留给 qa 回填）。AC 的描述引用 2.1 的名词与 2.3 的失败类别，不引入新概念。数量以"覆盖目标行为 + 覆盖失败归属表每一行"为准，不凑数。
4. **非目标** —— 至少一条。这是 dev 的硬边界，也是评审否决 Speculative Generality 的依据。
5. **资源** —— 引用的文件放进 `tasks/specs/<id>/`，用相对路径 `<id>/xxx` 引用；无则写"无"。
6. **变更记录** —— spec 定稿后任何改动（含仲裁改判）都追加一行：日期、变更、责任方。

## 落笔顺序

先 `taskctl add "<标题>"` 拿到 id 与骨架文件，再填内容——避免手建文件破坏注册一致性。填完自查一遍第 3 节：每条 AC 的判定命令现在就能原样敲进终端吗？不能，就还没写完。
